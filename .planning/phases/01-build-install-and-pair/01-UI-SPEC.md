# Phase 01 - UI Design Contract

> Visual and interaction contract for the first native iPhone screen. Native SwiftUI, not web.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker. Written without user answers: every
> default taken is listed under "Assumptions" at the end and can be changed.

Scope: ONE screen, `ContentView`, in the four-file, 400-line app target of Plan 01-04. Pair form,
status line, About (version/build/commit), Log export. No photo-library, backup, progress or
settings screens. No new files, no new Core types: this spec constrains how `ContentView` and the
strings in `AppModel` look and read, nothing else.

Hard rules inherited from the plans (the executor and the CI greps enforce these):

- Swift sources contain none of the words `backed up`, `backup`, `synced`, `protected` (case
  insensitive, CI grep). No wording anywhere on this screen says or implies photos were saved,
  copied, secured or counted. A connection is never presented as a backup.
- No `import Photos` / `PhotosUI`. No third-party package. No previews. No asset catalog, no
  custom fonts, no custom colours, no icon artwork.
- The device key and pairing code are never displayed, logged or placed in an accessibility label.
- A success look (green check, "Connected to") appears only after `checkConnection()` returned
  `.reachable` (server-confirmed). A stored pairing alone is never drawn as success.

## Screen Layout

One `NavigationStack` containing one `Form` (inset grouped list). Navigation title "Mewt Photos",
`.navigationBarTitleDisplayMode(.inline)`. No tab bar, no toolbar items, no sheets of our own.

Section order, top to bottom (all content scrolls; nothing is pinned):

| # | Section | Header | Rows | Footer |
|---|---------|--------|------|--------|
| 1 | Status | none | Status row (symbol + text, see below) | none |
| 2 | Pair | "Pair with your PC" | PC address field; Pairing code field; Pair button; error row (only when an error exists) | See Copywriting: instructions + Local Network hint |
| 3 | Log | "Log" | Export log (`ShareLink`) | Where the same file is in Files |
| 4 | About | "About" | "Version ..." line; "Commit ..." line | none |

Rules:

- The Pair section is ALWAYS visible, including when already paired and when in any repair state.
  Re-pairing overwrites key and record (Plan 01-04). Forget / edit address is Phase 4 (PAIR-05) and
  is not built or hinted at here.
- Focal point: the Status row is read first, and the Pair button is the only filled control on the
  screen. Nothing else competes with those two.
- Status is first so the answer to "does it work?" is visible without scrolling at every Dynamic
  Type size.
- Keyboard: the `Form` scrolls the focused field into view (default). `.scrollDismissesKeyboard(.interactively)`.
- Single column, no landscape layout, no iPad layout.

### Status row

`HStack(alignment: .firstTextBaseline, spacing: 8)` of a symbol and one `Text`, wrapped as a single
accessibility element (`.accessibilityElement(children: .combine)`); the symbol is
`accessibilityHidden(true)` so VoiceOver reads only the text. Text is `.title3` regular,
`.primary`, multi-line, no truncation (`lineLimit(nil)`, `fixedSize(horizontal: false, vertical: true)`).
The symbol colour never carries meaning alone; the text always states the state.

| State (model) | Text (verbatim from Plan 01-04) | Symbol | Symbol colour |
|---------------|---------------------------------|--------|---------------|
| `pairingState == nil` (before `start()` finishes) | "Starting..." (three ASCII dots) | `ProgressView` (small) in place of symbol | system |
| `.unpaired` | "Not paired yet" | `circle.dashed` | `.secondary` |
| `.paired`, connection check running | "Paired with " + server name | `ProgressView` (small) | system |
| connection result `.reachable` | "Connected to " + server name | `checkmark.circle.fill` | `.green` |
| connection result `.unreachable` | "Cannot reach your PC right now. " + Core message | `exclamationmark.triangle.fill` | `.orange` |
| connection result `.keyRejected` | "The PC no longer accepts this iPhone. Pair again with a new code from the PC." | `exclamationmark.triangle.fill` | `.orange` |
| `.needsRepair(.keyMissing)` | "This iPhone lost its pairing key. Pair again with a new code from the PC." | `exclamationmark.triangle.fill` | `.orange` |
| `.needsRepair(.recordUnreadable)` | "The saved pairing could not be read. Pair again." | `exclamationmark.triangle.fill` | `.orange` |
| `.needsRepair(.keychainError(n))` | "The iPhone key store returned error " + n + ". Pair again, and export the log if it repeats." | `exclamationmark.triangle.fill` | `.orange` |

Notes:

- "Paired with ..." (no check, no green) is shown only while the check runs or if the check never
  ran; it must never persist as the final state after `checkConnection()` returns.
- Server name is user/PC-supplied text: render as plain `Text`, wrap, never truncate with an ellipsis.
- Never display the stored address, device id or key in the status row. (Address and server name
  are fine; they are not secrets. Device key and pairing code are.)

### Pair section

| Row | Control | Spec |
|-----|---------|------|
| PC address | `TextField("PC address", text:, prompt: Text("192.168.1.20:8787"))` | `.keyboardType(.URL)`, `.textInputAutocapitalization(.never)`, `.autocorrectionDisabled()`, `.textContentType(.URL)`, `.submitLabel(.next)`. Accessibility label "PC address" (the title string). |
| Pairing code | `TextField("Pairing code", text:, prompt: Text("8-character code"))` | `.textInputAutocapitalization(.characters)`, `.autocorrectionDisabled()`, `.submitLabel(.go)`, body size with `.monospaced()`. Submitting (Go) triggers Pair only when the Pair button would be enabled. Accessibility label "Pairing code". |
| Pair | `Button("Pair")` + inline `ProgressView` while busy | Full-width row: `.buttonStyle(.borderedProminent)`, `.controlSize(.large)`, `.frame(maxWidth: .infinity)`, `.listRowBackground(Color.clear)`. Label stays exactly "Pair" in every state (the device checklist looks for it). Disabled while `busy` or either field is empty (after trimming whitespace). While busy: small `ProgressView` beside the label, button disabled, `.accessibilityLabel("Pairing")`. |
| Error | `Text(errorText)` | Only when `errorText != nil`. `.body`, `.foregroundStyle(.red)` with a leading `exclamationmark.circle.fill` symbol (hidden from VoiceOver), multi-line, no truncation, `.accessibilityElement(children: .combine)`. Appears directly under the Pair button. Cleared at the start of the next Pair attempt. |

Behaviour:

- Fields keep what was typed after a failure, except the pairing code, which is cleared after any
  attempt that reached the PC (single-use code; Plan 01-04). An input-validation failure that never
  reached the PC (bad address, empty code) keeps both fields.
- No inline per-field validation while typing. Validation happens on Pair, using the Core's
  `userMessage` text.
- Success: the error row disappears and the Status row changes to "Paired with ..." then
  "Connected to ..." (the `pair` path ends with a server `status` call, so a connection result is
  available; if only the paired info is, show "Paired with ..." until a check completes).
- No success alert, toast, haptic or sheet. The status row is the only feedback.

### Log section

- `ShareLink(item: runLog.fileURL)` with `Label("Export log", systemImage: "square.and.arrow.up")`.
  This is the second place the accent colour appears. The file always exists (Core creates it at init),
  so the control is never disabled or hidden.
- The system share sheet is used as is (Save to Files, AirDrop, Mail). No custom preview, no custom
  share UI, no confirmation after sharing.

### About section

- Row 1: one `Text`, body: "Version " + marketing version + " (build " + build number + ")".
  Example: `Version 0.1.0 (build 12)`.
- Row 2: one `Text`, body, `.monospaced()`: "Commit " + `MewtPhotosGitSHA` exactly as read from
  Info.plist (no shortening in the view; CI decides the length; local builds show `dev`).
  `.textSelection(.enabled)` so the SHA can be copied.
- Missing plist values render as `unknown` rather than an empty string.
- No hint of AltStore expiry, update checks or credits (CONV-06 is v2).

## Spacing Scale

Declared values (multiples of 4; points, not px). The screen is stock `Form`, so almost all spacing
is the system's. Custom spacing is limited to these:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4pt | Not used by the screen; reserved |
| sm | 8pt | Gap between status/error symbol and its text (`HStack spacing: 8`) |
| md | 16pt | Not set manually; equals the system `Form` horizontal inset |
| lg | 24pt | Not set manually; section separation is the system's |
| xl | 32pt | Not used |
| 2xl | 48pt | Not used |
| 3xl | 64pt | Not used |

Exceptions: (1) `Form` row insets, row heights and section gaps are system-owned and are not
multiples of 4 in every case (for example the 11pt vertical row inset). Do not override them with
`.listRowInsets` or extra `.padding`. (2) Every tappable control must be at least 44 x 44pt; the
stock `Form` row and `.controlSize(.large)` button already meet this, so no custom frames are
needed. Do not shrink them.

## Typography

Text styles only, so Dynamic Type works from xSmall to AX5. Sizes shown are the default (Large)
content size; line height is the system's for that style (do not set `.lineSpacing`).

| Role | Style | Size | Weight | Line Height | Used for |
|------|-------|------|--------|-------------|----------|
| Status | `.title3` | 20pt | regular (400) | system, about 1.25 | Status row text |
| Body | `.body` | 17pt | regular (400) | system, about 1.3 | Field text and prompts, error text, About lines, Export log label |
| Emphasis | `.body` | 17pt | semibold (600) | system, about 1.3 | Pair button label (system prominent button), inline navigation title "Mewt Photos" |
| Footnote | `.footnote` | 13pt | regular (400) | system, about 1.4 | Section headers and footers (system `Form` styling, uppercased headers are the system default) |

Declared sizes: 3 (20, 17, 13). Declared weights: 2 (regular 400, semibold 600). No bold, no
light, no italic, no `.largeTitle`.

Dynamic Type requirements (no device iteration is available, so these are rules, not suggestions):

- Nothing is clipped or truncated at any size: no `lineLimit(1)`, no fixed heights, no
  `minimumScaleFactor`.
- At accessibility sizes the status text, the error text and the footers simply wrap and the
  `Form` scrolls. Do not hide the symbol or the hint at large sizes.
- The pairing code and commit SHA use `.monospaced()` on the same text style, never a smaller size.

## Color

System semantic colours only. They adapt to light/dark and Increase Contrast automatically. The hex
values below are reference values for the default appearance; do NOT hard-code them. There is no
asset catalog and no `AccentColor`, so the tint is the system default blue.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `systemGroupedBackground` (about #F2F2F7 light, #000000 dark) | Screen background behind the `Form` (default) |
| Secondary (30%) | `secondarySystemGroupedBackground` (about #FFFFFF light, #1C1C1E dark) | Form section cards / rows (default) |
| Accent (10%) | system tint, `systemBlue` (about #007AFF light, #0A84FF dark) | Reserved list below |
| Destructive | none in this phase | There are no destructive actions (no forget / delete). Do not introduce a red button. |
| Text | `.primary` for content, `.secondary` for hints/footers/placeholders | Never a custom grey |

State colours (semantic, used only on the leading symbol or error text, never as the sole signal):

| Meaning | Colour | Where |
|---------|--------|-------|
| Server-confirmed connected | `.green` | `checkmark.circle.fill` in Status, only for "Connected to" |
| Needs attention | `.orange` | `exclamationmark.triangle.fill` in Status |
| Pairing attempt failed | `.red` | Error row text and its symbol |
| Neutral / not set up | `.secondary` | `circle.dashed` |

Accent reserved for: (1) the fill of the Pair button, (2) the "Export log" `ShareLink` label and its
symbol, (3) the text-field caret and selection (system default). Nothing else is tinted: not the
Status row, not the About rows, not section headers. Do not set `.tint` or `.accentColor` anywhere.

Contrast: text is always `.primary` / `.secondary` on system backgrounds (system-guaranteed). The
white label on the prominent blue Pair button and the disabled dimming are system behaviour and are
accepted as is.

## Interaction and Accessibility Contract

- Every interactive control has a text label that VoiceOver reads: "PC address", "Pairing code",
  "Pair" (or "Pairing" while busy), "Export log". Placeholders are not the only label.
- Decorative symbols are `accessibilityHidden(true)`; meaning is in the text.
- Tab / reading order is top to bottom as listed in Screen Layout.
- Controls are system controls, so Bold Text, Reduce Motion, Increase Contrast, Reduce
  Transparency and Voice Control work without extra code.
- No custom animation; the only motion is the system `ProgressView` and normal keyboard handling.
- No haptics, sounds, alerts, confirmation dialogs or sheets of our own. The only system UI that
  may appear is the iOS Local Network permission dialog and the share sheet.
- The device key, pairing code and device id never appear in any accessibility label, value or hint.

## Assumptions (made in place of user answers, change any of them)

1. Single screen with a `NavigationStack` and inline title "Mewt Photos", rather than a bare `Form`.
2. The Pair form stays visible after pairing succeeds (no separate "paired" screen). Needed anyway for repair states; it avoids a second layout.
3. Pair button is a full-width prominent (filled) button, not a plain text-style `Form` row button.
4. Status text is `.title3` regular so long unreachable/repair messages stay readable; semibold is reserved for the Pair button and the system title.
5. State symbols and colours: green check only for "Connected to"; orange triangle for every attention state; red only for a failed Pair attempt. No red or destructive buttons.
6. Section order Status, Pair, Log, About, and header titles "Pair with your PC", "Log", "About".
7. Field prompts "192.168.1.20:8787" and "8-character code" (8 characters from `server/security.ts` pairing codes).
8. "Starting..." shown before `start()` completes, so a paired phone never flashes "Not paired yet".
9. About second line reads "Commit <sha>" in monospaced type, with text selection enabled; unknown values print `unknown`.
10. System appearance only (light/dark follows iOS). Portrait only, iPhone only, English only, no app icon or launch artwork (all deferred by the skeleton).
11. No accent colour customisation: tint is the default system blue because the plans forbid an asset catalog.
12. No success haptic, toast or alert after pairing; the status row is the confirmation.

Observations for the planner (not changed here, not in this spec's scope):

- DECIDED 2026-10-12 (reword, see Copywriting Contract). `ios/MewtPhotos/Info.plist` `NSLocalNetworkUsageDescription` reads "Mewt Photos connects to your PC on this Wi-Fi network to back up your photos." That system dialog is shown on the first Pair in Phase 1, when nothing is backed up yet, and it is outside the Swift-source word grep. It slightly conflicts with the Phase 1 "connection is not a backup" rule. Consider "Mewt Photos connects to your PC on this Wi-Fi network." (the Info.plist gate only needs the key to be non-empty; confirm against `ios/scripts/check_info_plist.py` before editing). `NSPhotoLibraryUsageDescription` and `NSCameraUsageDescription` are never triggered in Phase 1.
- Plan 01-04 acceptance criteria require the literal `"Cannot reach your PC right now. "` (with trailing space) inside `AppModel.swift`, so the status stays one string per state. This spec therefore does NOT split status into title and detail.
